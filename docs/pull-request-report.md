# Pull request body and processing report

When the action creates a pull request, it fills the PR description from a JSON processing report
produced by TODO Registrar during the scan.

This gives reviewers a structured summary of what changed and which tracker issues were created
or reused — without reading the full diff first.

## When a pull request is created

A pull request is opened only when **all** of the following are true:

- processing was not skipped (`skipped: false`),
- `new_branch_name` resolves to a branch different from `target_branch_name`,
- TODO Registrar produced file changes that were committed (`has_changes: true`).

The PR uses a fixed title:

```text
[TODO Registrar] automated registering of new TODOs
```

The body is generated by [`scripts/build-pr-body.sh`](../scripts/build-pr-body.sh)
from the report file written during the **Run TODO Registrar** step.

See [How it works](how-it-works.md#create-a-pull-request) for the full workflow.

## Processing report

During the Docker run, TODO Registrar writes a JSON report to:

```text
${RUNNER_TEMP}/todo-registrar-report.json
```

The action passes these CLI flags:

```text
--report-format=json --report-path=/runner-temp/todo-registrar-report.json
```

### Report structure

The PR body script reads the following fields:

| JSON path | Used for |
|-----------|----------|
| `summary.todos.registered` | TODO comments that received an issue key |
| `summary.todos.newIssues` | New issues created in the tracker |
| `summary.todos.glued` | TODOs linked to an existing issue key |
| `summary.files.analyzed` | Optional — number of scanned files (shown when nothing was registered) |
| `issues[].key` | Issue key inserted during the run (for **Created issues**) |
| `issues[].usageCounter` | How many TODO comments received that key |
| `files[].path` | Source file path |
| `files[].summary.todos.registered` | Registered TODO count per file (for **Updated files**) |

The `issues` array is optional. When TODO Registrar includes it in the report, the PR body shows a
**Created issues** section. See [TODO Registrar report](https://github.com/Aeliot-Tm/todo-registrar/blob/main/docs/report.md#issues).

Minimal example:

```json
{
  "summary": {
    "todos": {
      "registered": 7,
      "newIssues": 5,
      "glued": 2
    }
  },
  "issues": [
    {
      "key": "PROJ-101",
      "usageCounter": 1
    },
    {
      "key": "PROJ-102",
      "usageCounter": 2
    }
  ],
  "files": [
    {
      "path": "src/Service/Foo.php",
      "summary": {
        "todos": {
          "registered": 3
        }
      }
    }
  ]
}
```

The report stays in the runner temp directory and is **not** committed to the repository.
The same JSON is available as the action output `summary_report` when processing runs.
See [Using outputs](outputs.md#processing-report). Only the generated PR body is published on GitHub.

## Pull request body layout

The body is built from HTML tables and Markdown collapsible sections (`<details>`).

### Header table

The logo and main content share one table. The logo links to the
[TODO Registrar Action](https://github.com/marketplace/actions/todo-registrar) on the GitHub Marketplace.

### Collapsible sections

When `registered > 0`, up to three accordions may follow the header table, in this order:

1. **Created issues (N)** — when the report contains a non-empty `issues` array; table of issue keys
   and TODO counts (`usageCounter`)
2. **Updated files (N)** — when at least one file has `summary.todos.registered > 0`; files sorted by
   registered TODO count (highest first)
3. **Metric definitions** — always shown; explains **Registered**, **New issues**, and **Glued**
